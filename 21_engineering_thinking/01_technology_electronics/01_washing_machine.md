# מכונת כביסה: מי מנהל את מחזור הכביסה?

**משך מומלץ:** 45–60 דקות  
**כלים שכבר למדנו:** משתנים, תנאים, for, מצב מערכת, פונקציות  
**תפקידכם:** צוות הנדסת תוכנה. עליכם להבין את הבעיה, לנתח מערכת קיימת, לבדוק אותה ולפתח גרסה משופרת.

## א. הסיפור והבעיה

מפעל מייצר מכונות כביסה. לקוחות מתלוננים שהמכונה מתחילה להפעיל את התוף עוד לפני שיש מספיק מים, ולעיתים מסיימת את הכביסה כשהמים עדיין בתוף. אתם צוות התוכנה: החיישנים מספקים מספרים, אבל התוכנה חייבת להחליט מה מותר לעשות בכל רגע.

בסימולציה כל מדידה היא יחידת זמן. במצב FILL הערך הוא כמות המים שנכנסה, במצב WASH הוא אינו משנה את המים, ובמצב DRAIN הוא כמות המים שיצאה. היעד הוא 6 יחידות מים ושני מחזורי שטיפה. מעבר מצב מתבצע בסוף אותה מדידה; פעולה של המצב החדש תתחיל רק במדידה הבאה. אין מדובר בבקר אמיתי.

## ב. לפני המחשב: חשבו כמו מהנדסים

ענו במחברת, לפני כתיבת קוד. הגדירו קלט, פלט, מידע שנשמר בין פעולות וכלל שהמערכת חייבת לשמור עליו תמיד.

1. איזה מידע צריך לזכור גם אחרי שהחיישן שלח נתון חדש?
2. מדוע אי אפשר להחליט לפי כמות המים בלבד אם לכבס או לרוקן?
3. שרטטו ארבעה מצבים וחצים ביניהם. האם מותר לחזור מ-DONE ל-FILL ללא התחלת תוכנית חדשה?

## ג. קריאת קוד ומעקב ידני

הקוד הבא הוא אב-טיפוס קיים שקיבלתם מצוות אחר. **אל תריצו אותו עדיין.** עברו שורה אחר שורה וחשבו מה קורה בפועל.

```python
def trace(readings):
    stage = "FILL"
    water = 0
    washed = 0

    for step, amount in enumerate(readings, 1):
        if stage == "FILL":
            water = min(6, water + amount)
            if water == 6:
                stage = "WASH"
        elif stage == "WASH":
            washed += 1
            if washed == 2:
                stage = "DRAIN"
        elif stage == "DRAIN":
            water = max(0, water - amount)
            if water == 0:
                stage = "DONE"

        print(step, stage, water, washed)

trace([3, 4, 2, 6, 4, 4, 3, 1])
```

1. השלימו את הטבלה; בעמודת המצב/הערך יש לרשום את הערך **בסוף** האיטרציה, אלא אם כתוב "לפני".
2. סמנו במפורש צעד שלא מתבצע בגלל עצירה. אם יש שורת פלט לאחר הלולאה, כתבו גם אותה.
3. הוסיפו טבלת מעקב מפורטת לאיטרציה אחת שיש בה החלטה משמעותית: שורת קוד, משתנה שהשתנה, ערך קודם, ערך חדש, נימוק.
4. כתבו את הפלט המדויק, כולל סדר השורות. רק לאחר מכן הריצו והשוו.

## ד. מעקב נוסף: אותו קוד, קלט אחר

החליפו רק את הקריאה האחרונה לפונקציה ב-`trace([6, 0, 0, 2, 4])`. שוב אל תריצו לפני שהשלמתם את הטבלה.

| מדידה | amount | stage בסוף | water | washed | האם התבצע מעבר מצב? |
| --- | --- | --- | --- | --- | --- |
| 1 | 6 |   |   |   |   |
| 2 | 0 |   |   |   |   |
| 3 | 0 |   |   |   |   |

כתבו את הפלט המדויק. השוו בין שני הקלטים: באיזה שלב התנהגות המערכת משתנה ומדוע? הוסיפו קלט שלישי משלכם שיגרום למסלול החלטה שונה או שיבדוק ערך גבול.

## ה. שאלות חשיבה וביקורת קוד

1. באיזו מדידה הכביסה מתחילה בפועל? הסבירו את ההבדל בין מעבר ל-WASH לבין ביצוע שטיפה.
2. מה היה קורה אילו היינו מחליפים את elif השני ב-if נפרד? עקבו אחרי המדידה השנייה והסבירו מדוע התוצאה שונה.
3. למה min ו-max נדרשים? תנו דוגמה לנתון שמפר כל מגבלה ללא הפונקציה.
4. אם המדידות נגמרות כשהמצב DRAIN, האם נכון להציג DONE? מה המידע שחסר למשתמש?

**תקלה מכוונת:** מתכנת מציע להחליף את `elif stage == "WASH":` ב-`if stage == "WASH":`. מצאו את המדידה הראשונה שבה התוצאה שונה וכתבו תיקון. בדקו גם האם ה-elif של DRAIN יושפע ממבנה התנאים החדש.

כתבו מה הדרישה שנפגעת, מה הקלט הקטן ביותר שמדגים זאת, מה התקבל בפועל ומה היה אמור להתקבל.

## ו. עכשיו אתם המפתחים

כתבו פונקציה `run_cycle(readings, target, wash_ticks)` המדמה תוכנית חדשה: היעד ומספר השטיפות משתנים בין תוכניות. כל הערכים שלמים. היעדים חייבים להיות חיוביים; מדידה שלילית לפני סיום גורמת למצב ERROR בלי לעדכן מים או שטיפות. עצרו מיד ב-DONE או ERROR והתעלמו מהמדידות הבאות. החזירו `(stage, water, washed, used)` כאשר used הוא מספר המדידות שנקראו, כולל מדידה שגויה. יעד לא תקין מחזיר `("ERROR", 0, 0, 0)`. רשימה ריקה ויעדים תקינים מחזירה מצב FILL.

**דרך עבודה:**
- נסחו לפחות שלושה כללים שהמערכת חייבת לשמור עליהם. הגדירו מה קורה בקלט ריק, בקלט חריג ובערך גבול.
- כתבו פסאודו-קוד או תרשים זרימה לפני הפתרון. ציינו מתי משתנה המצב, מתי הנתונים מתעדכנים ומתי עוצרים.
- כתבו פונקציה עצמאית עם שמות משתנים בעלי משמעות. אל תשנו את הקוד הקיים; הוא משמש להשוואה.
- הוסיפו קריאות לפונקציה עם `print`. אין צורך ב-input בשלב הזה כדי שכל הצוותים יוכלו להריץ אותם מקרי בדיקה. מי שמסיים יכול להוסיף ממשק input בנפרד.

## ז. בדיקות קבלה

לפני הרצה, חשבו מדוע כל מקרה חשוב. אחרי ההרצה מלאו את התוצאה בפועל והחליטו אם הבדיקה עברה.

| # | קלט | פלט צפוי (ערך מוחזר) | פלט בפועל | עבר / נכשל |
| --- | --- | --- | --- | --- |
| 1 | `run_cycle([3, 4, 2, 6, 4, 4, 3, 1], 6, 2)` | `("DONE", 0, 2, 6)` | | |
| 2 | `run_cycle([2, -1, 8], 6, 2)` | `("ERROR", 2, 0, 2)` | | |
| 3 | `run_cycle([6, 0], 6, 2)` | `("WASH", 6, 1, 2)` | | |
| 4 | `run_cycle([], 6, 2)` | `("FILL", 0, 0, 0)` | | |
| 5 | `run_cycle([5], 0, 2)` | `("ERROR", 0, 0, 0)` | | |
| 6 | `run_cycle([2, 0, 2], 2, 1)` | `("DONE", 0, 1, 3)` | | |

הוסיפו לפחות שלוש בדיקות משלכם: מקרה גבול, מקרה תקלה ומקרה שמוכיח כלל מרכזי. אם בדיקה נכשלת, שמרו את הקלט לפני תיקון, תקנו והפעילו את כל הבדיקות שוב.

## ח. שינוי דרישות מהלקוח

הוסיפו מצב PAUSE כאשר הדלת נפתחת. תכננו איך לזכור את המצב הקודם ואיך להמשיך מבלי לספור שטיפה כפולה. הציעו שני רצפי בדיקה: פתיחה בזמן מילוי ופתיחה בזמן ריקון. הסבירו איזה כלל בטיחות בסימולציה אסור להפר.

1. כתבו מה השתנה בדרישות ומה לא.
2. ציינו אילו משתנים, תנאים ופונקציות יושפעו מהשינוי.
3. הציעו פסאודו-קוד. אם נשאר זמן, ממשו את ההרחבה בקובץ נפרד והדגימו פלט.
4. כתבו בדיקה אחת שמוכיחה שגרסת הבסיס לא נשברה ובדיקה אחת לדרישה החדשה.

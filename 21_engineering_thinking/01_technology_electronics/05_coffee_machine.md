# מכונת קפה: הזמנה היא לא רק לחיצה על כפתור

**משך מומלץ:** 60–75 דקות  
**כלים שכבר למדנו:** מילונים, תנאים, לולאות, מלאי, פעולה אטומית, פונקציות  
**תפקידכם:** צוות הנדסת תוכנה. עליכם להבין את הבעיה, לנתח מערכת קיימת, לבדוק אותה ולפתח גרסה משופרת.

## א. הסיפור והבעיה

הקפטריה מתקינה מכונת קפה אוטומטית. תקלה גורמת למכונה להפחית קפה גם כאשר אין מספיק חלב, ובמקרים אחרים לחייב לקוח אף שלא הכינה משקה. צוות הפיתוח חייב להגדיר מתי עסקה נחשבת מוצלחת.

לצורך ההדמיה המלאי הוא שלוש יחידות של משאבים: קפה, מים וחלב, והמתכונים הם כמויות דמיוניות. אספרסו E דורש (1,2,0), לאטה L דורש (2,3,2), גדול G דורש (3,4,3). אין טיפול אמיתי בחומרי מזון או תשלומים.

## ב. לפני המחשב: חשבו כמו מהנדסים

ענו במחברת, לפני כתיבת קוד. הגדירו קלט, פלט, מידע שנשמר בין פעולות וכלל שהמערכת חייבת לשמור עליו תמיד.

1. למה כדאי לשמור מתכונים במילון ולא לחזור על אותן בדיקות לכל משקה?
2. מה חייבים לבדוק לפני שמורידים את המלאי?
3. מה המשמעות של עסקה אטומית: או שכל העדכונים הצליחו או שאף אחד מהם לא בוצע?

## ג. קריאת קוד ומעקב ידני

הקוד הבא הוא אב-טיפוס קיים שקיבלתם מצוות אחר. **אל תריצו אותו עדיין.** עברו שורה אחר שורה וחשבו מה קורה בפועל.

```python
def trace(orders):
    recipes = {"E": (1, 2, 0), "L": (2, 3, 2), "G": (3, 4, 3)}
    coffee, water, milk = 7, 9, 5
    served = 0
    for step, order in enumerate(orders, 1):
        c, w, m = recipes[order]
        if coffee >= c and water >= w and milk >= m:
            coffee -= c
            water -= w
            milk -= m
            served += 1
            status = "SERVED"
        else:
            status = "REJECTED"
        print(step, order, status, coffee, water, milk, served)

trace(["L", "E", "L", "G", "E"])
```

1. השלימו את הטבלה; בעמודת המצב/הערך יש לרשום את הערך **בסוף** האיטרציה, אלא אם כתוב "לפני".
2. סמנו במפורש צעד שלא מתבצע בגלל עצירה. אם יש שורת פלט לאחר הלולאה, כתבו גם אותה.
3. הוסיפו טבלת מעקב מפורטת לאיטרציה אחת שיש בה החלטה משמעותית: שורת קוד, משתנה שהשתנה, ערך קודם, ערך חדש, נימוק.
4. כתבו את הפלט המדויק, כולל סדר השורות. רק לאחר מכן הריצו והשוו.

## ד. מעקב נוסף: אותו קוד, קלט אחר

החליפו רק את הקריאה האחרונה לפונקציה ב-`trace(["G", "G", "E", "L"])`. שוב אל תריצו לפני שהשלמתם את הטבלה.

| הזמנה | סוג | דרישות c,w,m | status | coffee | water | milk | served |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | G |   |   |   |   |   |   |
| 2 | G |   |   |   |   |   |   |
| 3 | E |   |   |   |   |   |   |
| 4 | L |   |   |   |   |   |   |

כתבו את הפלט המדויק. השוו בין שני הקלטים: באיזה שלב התנהגות המערכת משתנה ומדוע? הוסיפו קלט שלישי משלכם שיגרום למסלול החלטה שונה או שיבדוק ערך גבול.

## ה. שאלות חשיבה וביקורת קוד

1. באיזו הזמנה בקלט הראשון נשאר קפה אך אין מספיק מים?
2. בדקו אם החלפת `and` ב-`or` באמת גורמת לטעות בהזמנה 4. אם לא, מצאו את ההזמנה הראשונה שבה היא כן גורמת למלאי שלילי, והסבירו מדוע.
3. למה אפשר להכין אספרסו גם אם החלב אזל?
4. האם סדר ההזמנות משנה את מספר המשקאות שאפשר להכין? בנו שני סדרים עם אותם משקאות ותוצאה שונה, או הסבירו מה גורם להבדל.

**תקלה מכוונת:** המפתחת כתבה `coffee -= c` לפני הבדיקה של כל הרכיבים. הדגימו בקלט השני (הזמנה 2) מדוע המלאי משתבש גם אם אין משקה. שרטטו סדר פעולות תקין.

כתבו מה הדרישה שנפגעת, מה הקלט הקטן ביותר שמדגים זאת, מה התקבל בפועל ומה היה אמור להתקבל.

## ו. עכשיו אתם המפתחים

כתבו `serve(orders, stock)` כאשר stock הוא tuple של (coffee, water, milk), ו-orders היא רשימת זוגות (סוג משקה, סכום שהוכנס). המחירים E=8, L=12, G=15. לכל הזמנה תקינה: בדקו גם תשלום וגם את כל הרכיבים; רק אם הכל מספיק, הפחיתו מלאי, הוסיפו את המחיר להכנסות והחזירו עודף. אם סוג לא מוכר, תשלום שלילי, חוסר כסף או חוסר מלאי: דחו, אל תשנו מלאי או הכנסות, רשמו בקבלה את כל הכסף להחזרה (לתשלום שלילי רשמו 0). אם מלאי התחלתי שלילי, החזירו `(stock, 0, [])` ללא טיפול. החזירו `(stock_final, revenue, receipts)`; כל קבלה היא `(status, refund)` כאשר status הוא SERVED/REJECTED ו-refund הוא עודף או החזר מלא. כל הערכים שלמים והמבנים תקינים.

**דרך עבודה:**
- נסחו לפחות שלושה כללים שהמערכת חייבת לשמור עליהם. הגדירו מה קורה בקלט ריק, בקלט חריג ובערך גבול.
- כתבו פסאודו-קוד או תרשים זרימה לפני הפתרון. ציינו מתי משתנה המצב, מתי הנתונים מתעדכנים ומתי עוצרים.
- כתבו פונקציה עצמאית עם שמות משתנים בעלי משמעות. אל תשנו את הקוד הקיים; הוא משמש להשוואה.
- הוסיפו קריאות לפונקציה עם `print`. אין צורך ב-input בשלב הזה כדי שכל הצוותים יוכלו להריץ אותם מקרי בדיקה. מי שמסיים יכול להוסיף ממשק input בנפרד.

## ז. בדיקות קבלה

לפני הרצה, חשבו מדוע כל מקרה חשוב. אחרי ההרצה מלאו את התוצאה בפועל והחליטו אם הבדיקה עברה.

## ח. שינוי דרישות מהלקוח

המכונה מחזירה עודף רק במטבעות 1, 2 ו-5 ויש מלאי מוגבל של כל מטבע. תכננו בדיקת אפשרות להחזיר עודף לפני חיוב. האם בחירה תמיד במטבע הגדול ביותר מבטיחה פתרון כאשר מלאי המטבעות מוגבל? בדקו למשל עודף 6 עם מטבע 5 אחד, שלושה מטבעות 2 ואפס מטבעות 1.

1. כתבו מה השתנה בדרישות ומה לא.
2. ציינו אילו משתנים, תנאים ופונקציות יושפעו מהשינוי.
3. הציעו פסאודו-קוד. אם נשאר זמן, ממשו את ההרחבה בקובץ נפרד והדגימו פלט.
4. כתבו בדיקה אחת שמוכיחה שגרסת הבסיס לא נשברה ובדיקה אחת לדרישה החדשה.

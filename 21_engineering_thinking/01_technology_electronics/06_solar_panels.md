# פאנלים סולאריים: מתי לאגור, מתי לקנות ומתי למכור?

**משך מומלץ:** 60–75 דקות  
**כלים שכבר למדנו:** לולאות, משתנים צוברים, min/max, תנאים, שימור משאב  
**תפקידכם:** צוות הנדסת תוכנה. עליכם להבין את הבעיה, לנתח מערכת קיימת, לבדוק אותה ולפתח גרסה משופרת.

## א. הסיפור והבעיה

בית ספר מתקין פאנלים סולאריים וסוללה. מנהלת בית הספר רוצה לצמצם רכישת חשמל מהרשת, אבל כאשר הסוללה מלאה אי אפשר להמשיך לאגור. אתם מפתחים סימולטור למדיניות שימוש באנרגיה לאורך היום.

כל צמד מספרים מתאר יחידות אנרגיה באותו פרק זמן, לא הספק ולא מודל הנדסי אמיתי. תחילה משווים ייצור לצריכה. עודף נכנס לסוללה עד קיבולת 6 והשאר מועבר לרשת; חוסר מושלם מהסוללה ואז מהרשת. סוללה התחלתית 2. אין הפסדי אנרגיה.

## ב. לפני המחשב: חשבו כמו מהנדסים

ענו במחברת, לפני כתיבת קוד. הגדירו קלט, פלט, מידע שנשמר בין פעולות וכלל שהמערכת חייבת לשמור עליו תמיד.

1. למה לא מספיק לחשב את סך הייצור והצריכה בסוף היום?
2. מה ההבדל בין כמות אגורה בסוללה לבין חשמל שנרכש עד כה?
3. נסחו משוואת שימור אנרגיה לכל פרק זמן.

## ג. קריאת קוד ומעקב ידני

הקוד הבא הוא אב-טיפוס קיים שקיבלתם מצוות אחר. **אל תריצו אותו עדיין.** עברו שורה אחר שורה וחשבו מה קורה בפועל.

```python
def trace(periods):
    battery, imported, exported = 2, 0, 0
    for step, (generated, demand) in enumerate(periods, 1):
        net = generated - demand
        if net >= 0:
            stored = min(net, 6 - battery)
            battery += stored
            exported += net - stored
        else:
            missing = -net
            taken = min(missing, battery)
            battery -= taken
            imported += missing - taken
        print(step, net, battery, imported, exported)

trace([(1,5), (12,4), (1,5), (9,3), (0,8)])
```

1. השלימו את הטבלה; בעמודת המצב/הערך יש לרשום את הערך **בסוף** האיטרציה, אלא אם כתוב "לפני".
2. סמנו במפורש צעד שלא מתבצע בגלל עצירה. אם יש שורת פלט לאחר הלולאה, כתבו גם אותה.
3. הוסיפו טבלת מעקב מפורטת לאיטרציה אחת שיש בה החלטה משמעותית: שורת קוד, משתנה שהשתנה, ערך קודם, ערך חדש, נימוק.
4. כתבו את הפלט המדויק, כולל סדר השורות. רק לאחר מכן הריצו והשוו.

## ד. מעקב נוסף: אותו קוד, קלט אחר

החליפו רק את הקריאה האחרונה לפונקציה ב-`trace([(8,2), (2,2), (0,3), (0,5)])`. שוב אל תריצו לפני שהשלמתם את הטבלה.

| פרק זמן | ייצור, צריכה | net | סוללה לפני | סוללה אחרי | imported מצטבר | exported מצטבר |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 8, 2 |   |   |   |   |   |
| 2 | 2, 2 |   |   |   |   |   |

כתבו את הפלט המדויק. השוו בין שני הקלטים: באיזה שלב התנהגות המערכת משתנה ומדוע? הוסיפו קלט שלישי משלכם שיגרום למסלול החלטה שונה או שיבדוק ערך גבול.

## ה. שאלות חשיבה וביקורת קוד

1. חשבו את כמות הרכישה והייצוא בכל פרק בנפרד, ולא רק את המצטבר.
2. באיזה פרק הסוללה מלאה ובכל זאת נוצר עודף? למה?
3. בדקו בקלט הראשון את משוואת השימור: סכום ייצור + רכישה + סוללה התחלתית = צריכה + ייצוא + סוללה סופית.
4. מדוע ייתכן שיום עם ייצור גבוה עדיין מצריך רכישה מהרשת? תנו דוגמה של שני פרקי זמן.

**תקלה מכוונת:** מישהו כתב `battery += net` בכל פעם שיש עודף, בלי מגבלת קיבולת. הראו מה קורה בפרק 2 של הקלט הראשון, כולל המשמעות לדוח הייצוא. תקנו את חישוב stored.

כתבו מה הדרישה שנפגעת, מה הקלט הקטן ביותר שמדגים זאת, מה התקבל בפועל ומה היה אמור להתקבל.

## ו. עכשיו אתם המפתחים

כתבו `energy_day(periods, capacity, battery, reserve)`. capacity ו-reserve שלמים ולא שליליים, ו-`0 <= reserve <= battery <= capacity` חייב להתקיים בהתחלה; אחרת החזירו `(battery,0,0,"ERROR")`. בכל פרק זוג של ייצור וצריכה שלמים ולא שליליים, ערך שלילי עוצר ERROR לפני עיבוד הפרק. במקרה חוסר אין לרדת מתחת לרזרבה (נקנה מהרשת את היתרה); במקרה עודף ממלאים עד capacity ומייצאים את השאר. החזירו `(battery, imported, exported, status)` עם DONE לאחר כל הפרקים. אין לשנות את רשימת הקלט.

**דרך עבודה:**
- נסחו לפחות שלושה כללים שהמערכת חייבת לשמור עליהם. הגדירו מה קורה בקלט ריק, בקלט חריג ובערך גבול.
- כתבו פסאודו-קוד או תרשים זרימה לפני הפתרון. ציינו מתי משתנה המצב, מתי הנתונים מתעדכנים ומתי עוצרים.
- כתבו פונקציה עצמאית עם שמות משתנים בעלי משמעות. אל תשנו את הקוד הקיים; הוא משמש להשוואה.
- הוסיפו קריאות לפונקציה עם `print`. אין צורך ב-input בשלב הזה כדי שכל הצוותים יוכלו להריץ אותם מקרי בדיקה. מי שמסיים יכול להוסיף ממשק input בנפרד.

לפני הרצה, חשבו מדוע כל מקרה חשוב. אחרי ההרצה מלאו את התוצאה בפועל והחליטו אם הבדיקה עברה.

## ח. שינוי דרישות מהלקוח

הוסיפו מחירי רכישה וייצוא שונים לכל פרק זמן. תכננו השוואה בין מדיניות ששומרת רזרבה קבועה לבין מדיניות שמשחררת רזרבה בזמן מחיר גבוה. הגדירו נתוני ניסוי, עלות כוללת וכלל שמונע ירידה מתחת לרזרבה המוגדרת לבטיחות הסימולציה. אין צורך לחזות מחירים.

1. כתבו מה השתנה בדרישות ומה לא.
2. ציינו אילו משתנים, תנאים ופונקציות יושפעו מהשינוי.
3. הציעו פסאודו-קוד. אם נשאר זמן, ממשו את ההרחבה בקובץ נפרד והדגימו פלט.
4. כתבו בדיקה אחת שמוכיחה שגרסת הבסיס לא נשברה ובדיקה אחת לדרישה החדשה.

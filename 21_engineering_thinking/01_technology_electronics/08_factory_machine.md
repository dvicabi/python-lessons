# מכונה במפעל: מתי חריגה בודדת הופכת לתקלה?

**משך מומלץ:** 60–75 דקות  
**כלים שכבר למדנו:** for, רצף חריגות, תנאים מורכבים, break, פונקציות, מדיניות ניטור  
**תפקידכם:** צוות הנדסת תוכנה. עליכם להבין את הבעיה, לנתח מערכת קיימת, לבדוק אותה ולפתח גרסה משופרת.

## א. הסיפור והבעיה

מפעל מפתח מערכת ניטור למכונת ייצור מדומה. חיישן מספק מדידות. אם התוכנה תעצור על כל חריגה קטנה, הייצור ייפגע; אם תתעלם מרצף חריגות, התקלה עלולה להחמיר. תפקידכם להבחין בין אירוע בודד, מגמה ותקלה.

מדידות הן מדדי עומס דמיוניים, לא ערכי בטיחות אמיתיים. בסימולציה חריגה היא ערך 75 ומעלה. שלוש חריגות רצופות גורמות STOPPED שנשמר עד סוף הקלט. ערך תקין מאפס את הרצף, לא את היסטוריית המדידות.

## ב. לפני המחשב: חשבו כמו מהנדסים

ענו במחברת, לפני כתיבת קוד. הגדירו קלט, פלט, מידע שנשמר בין פעולות וכלל שהמערכת חייבת לשמור עליו תמיד.

1. מדוע ספירה מצטברת של חריגות אינה זהה לספירת חריגות רצופות?
2. האם עצירה לאחר שלוש חריגות תמיד עדיפה על עצירה מיידית? מה הסיכון בכל החלטה?
3. איזה מידע צריך לשמור כדי שמפעיל יוכל להבין מדוע התוכנית עצרה?

## ג. קריאת קוד ומעקב ידני

הקוד הבא הוא אב-טיפוס קיים שקיבלתם מצוות אחר. **אל תריצו אותו עדיין.** עברו שורה אחר שורה וחשבו מה קורה בפועל.

```python
def trace(readings):
    streak = 0
    stopped = False
    for step, value in enumerate(readings, 1):
        if not stopped:
            if value >= 75:
                streak += 1
            else:
                streak = 0
            if streak >= 3:
                stopped = True
        if stopped:
            status = "STOPPED"
        elif streak > 0:
            status = "WARNING"
        else:
            status = "NORMAL"
        print(step, value, streak, status)

trace([48,75,78,65,82,83,84,60])
```

1. השלימו את הטבלה; בעמודת המצב/הערך יש לרשום את הערך **בסוף** האיטרציה, אלא אם כתוב "לפני".
2. סמנו במפורש צעד שלא מתבצע בגלל עצירה. אם יש שורת פלט לאחר הלולאה, כתבו גם אותה.
3. הוסיפו טבלת מעקב מפורטת לאיטרציה אחת שיש בה החלטה משמעותית: שורת קוד, משתנה שהשתנה, ערך קודם, ערך חדש, נימוק.
4. כתבו את הפלט המדויק, כולל סדר השורות. רק לאחר מכן הריצו והשוו.

## ה. שאלות חשיבה וביקורת קוד

1. באיזו מדידה מתרחשת עצירה בקלט הראשון? מדוע מדידה 8 אינה מאפסת אותה?
2. כמה חריגות יש בסך הכל בקלט השני ומה הרצף הארוך ביותר?
3. מה ההבדל בין `>= 3` ל-`== 3` אם מונה החריגות עשוי להתחיל מערך משוחזר של 4?
4. הציעו מדד נוסף שיעזור להבדיל בין חריגה קטנה וקצרה לבין מצב חמור ומיידי.

**תקלה מכוונת:** החליפו את `streak = 0` ב-`pass` כאשר המדידה תקינה. עקבו בקלט השני ומצאו באיזה שלב המערכת תעצור בטעות. תקנו את הלוגיקה.

כתבו מה הדרישה שנפגעת, מה הקלט הקטן ביותר שמדגים זאת, מה התקבל בפועל ומה היה אמור להתקבל.

## ו. עכשיו אתם המפתחים

כתבו `monitor(readings)` שבו כל פריט הוא (load, vibration), שניהם מספרים שלמים. ערכים חוקיים: load בטווח 0–100 ו-vibration בטווח 0–20. נתון מחוץ לטווח מחזיר STOPPED עם reason=INVALID לפני עדכון streak; ערך load>=90 או vibration>=12 הוא CRITICAL ועוצר מיד לפני עדכון streak. אחרת, חריגה רגילה היא load>=75 או vibration>=8; חריגה מגדילה streak, מדידה תקינה מאפסת. אחרי שלוש חריגות רצופות עוצרים עם reason=STREAK. החזירו `(status, streak, stop_index, reason)`, מספר המדידה מתחיל ב-1. אם אין עצירה, status הוא WARNING כשהרצף חיובי או NORMAL כשאפס, ו-stop_index ו-reason הם None. בקלט ריק NORMAL. התעלמו מכל נתון אחרי העצירה.

**דרך עבודה:**
- נסחו לפחות שלושה כללים שהמערכת חייבת לשמור עליהם. הגדירו מה קורה בקלט ריק, בקלט חריג ובערך גבול.
- כתבו פסאודו-קוד או תרשים זרימה לפני הפתרון. ציינו מתי משתנה המצב, מתי הנתונים מתעדכנים ומתי עוצרים.
- כתבו פונקציה עצמאית עם שמות משתנים בעלי משמעות. אל תשנו את הקוד הקיים; הוא משמש להשוואה.
- הוסיפו קריאות לפונקציה עם `print`. אין צורך ב-input בשלב הזה כדי שכל הצוותים יוכלו להריץ אותם מקרי בדיקה. מי שמסיים יכול להוסיף ממשק input בנפרד.

## ז. בדיקות קבלה

לפני הרצה, חשבו מדוע כל מקרה חשוב. אחרי ההרצה מלאו את התוצאה בפועל והחליטו אם הבדיקה עברה.

| # | קלט | פלט צפוי (ערך מוחזר) | פלט בפועל | עבר / נכשל |
| --- | --- | --- | --- | --- |
| 1 | `monitor([(75,2),(70,8),(76,1),(0,0)])` | `("STOPPED",3,3,"STREAK")` | | |
| 2 | `monitor([(75,2),(70,2),(75,2)])` | `("WARNING",1,None,None)` | | |
| 3 | `monitor([(75,1),(90,0),(0,0)])` | `("STOPPED",1,2,"CRITICAL")` | | |
| 4 | `monitor([(80,1),(-1,12)])` | `("STOPPED",1,2,"INVALID")` | | |
| 5 | `monitor([])` | `("NORMAL",0,None,None)` | | |
| 6 | `monitor([(74,7),(74,8),(74,7)])` | `("NORMAL",0,None,None)` | | |

הוסיפו לפחות שלוש בדיקות משלכם: מקרה גבול, מקרה תקלה ומקרה שמוכיח כלל מרכזי. אם בדיקה נכשלת, שמרו את הקלט לפני תיקון, תקנו והפעילו את כל הבדיקות שוב.

## ח. שינוי דרישות מהלקוח

הציעו מדיניות נוספת: חלון מתגלגל של חמש מדידות, עצירה כאשר לפחות ארבע חריגות בחלון, גם אם אינן רצופות. חשבו על רצף שבו מדיניות זו עוצרת והקוד הקיים לא, ועל רצף הפוך. תעדו יתרונות וחסרונות והציעו בדיקות. כל הספים לצורכי הוראה בלבד.

1. כתבו מה השתנה בדרישות ומה לא.
2. ציינו אילו משתנים, תנאים ופונקציות יושפעו מהשינוי.
3. הציעו פסאודו-קוד. אם נשאר זמן, ממשו את ההרחבה בקובץ נפרד והדגימו פלט.
4. כתבו בדיקה אחת שמוכיחה שגרסת הבסיס לא נשברה ובדיקה אחת לדרישה החדשה.

## א. הסיפור והבעיה

חברה מפתחת אוזניות אלחוטיות עם סוללה בכל אוזנייה וסוללה בקופסה. משתמשים מתלוננים שאוזנייה אחת מתרוקנת הרבה לפני השנייה. אתם צריכים לבדוק את מדיניות הטעינה, ולתכנן מדיניות הוגנת יותר.

קיבולת כל אוזנייה היא 10 יחידות, קיבולת הקופסה 20. במצב B שתי האוזניות מנגנות וצורכות amount כל אחת, רק אם לשתיהן מספיק; במצב L/R רק האוזנייה הנבחרת צורכת; C מציין טעינה מהקופסה, עד amount לכל אוזנייה בניסוי הראשון, משמאל לימין. אין הפסדי אנרגיה במודל.

## ב. לפני המחשב: חשבו כמו מהנדסים

ענו במחברת, לפני כתיבת קוד. הגדירו קלט, פלט, מידע שנשמר בין פעולות וכלל שהמערכת חייבת לשמור עליו תמיד.

1. אילו שלושה מצבים מספריים צריך לזכור? מדוע ממוצע טעינה אינו מספיק?
2. הציעו מדיניות כששתי אוזניות צריכות טעינה אבל לקופסה אין מספיק לשתיהן.
3. אם נגינה נדחית, האם נכון להפחית אנרגיה מאוזנייה אחת בכל זאת? מדוע?

## ג. קריאת קוד ומעקב ידני

הקוד הבא הוא אב-טיפוס קיים שקיבלתם מצוות אחר. **אל תריצו אותו עדיין.** עברו שורה אחר שורה וחשבו מה קורה בפועל.

```python
def trace(events):
    left, right, case = 8, 10, 8
    for step, (mode, amount) in enumerate(events, 1):
        status = "OK"
        if mode == "B":
            if left >= amount and right >= amount:
                left -= amount
                right -= amount
            else:
                status = "DENIED"
        elif mode == "L":
            if left >= amount:
                left -= amount
            else:
                status = "DENIED"
        elif mode == "R":
            if right >= amount:
                right -= amount
            else:
                status = "DENIED"
        elif mode == "C":
            transfer = min(amount, 10 - left, case)
            left += transfer
            case -= transfer
            transfer = min(amount, 10 - right, case)
            right += transfer
            case -= transfer
        print(step, mode, status, left, right, case)

trace([("B",3), ("L",4), ("B",4), ("C",5), ("R",7), ("B",2)])
```

1. השלימו את הטבלה; בעמודת המצב/הערך יש לרשום את הערך **בסוף** האיטרציה, אלא אם כתוב "לפני".
2. סמנו במפורש צעד שלא מתבצע בגלל עצירה. אם יש שורת פלט לאחר הלולאה, כתבו גם אותה.
3. הוסיפו טבלת מעקב מפורטת לאיטרציה אחת שיש בה החלטה משמעותית: שורת קוד, משתנה שהשתנה, ערך קודם, ערך חדש, נימוק.
4. כתבו את הפלט המדויק, כולל סדר השורות. רק לאחר מכן הריצו והשוו.

## ה. שאלות חשיבה וביקורת קוד

1. מדוע צעד 3 בקלט הראשון לא משנה אף סוללה?
2. חשבו את סכום האנרגיה לפני ואחרי צעד 4. האם הטעינה יוצרת אנרגיה?
3. תנו קלט שבו הטעינה לשמאל תחילה אינה הוגנת ביחס לימין.
4. למה סדר הפחתת האנרגיה מהקופסה חשוב כשמבצעים טעינה לשני הצדדים?

**תקלה מכוונת:** דמיינו שהמתכנת חישב את שתי ההעברות לפני שהפחית את הראשונה מהקופסה. השתמשו במצב left=0, right=0, case=5, amount=5 כדי להוכיח מה ישתבש. תקנו את סדר הפעולות.

כתבו מה הדרישה שנפגעת, מה הקלט הקטן ביותר שמדגים זאת, מה התקבל בפועל ומה היה אמור להתקבל.

## ו. עכשיו אתם המפתחים

כתבו `manage_earbuds(events, left, right, case)`. נגינה B/L/R כמו בקוד הקיים; במקרה שאין מספיק אנרגיה, אין שינוי ומונה denied עולה ב-1. ב-C, amount הוא תקציב כולל לטעינה (לא לכל אוזנייה). העבירו יחידה בכל פעם לאוזנייה הפחות טעונה, ואם שוות אז לשמאל, עד גמר תקציב/קופסה/מקום. קיבולת אוזנייה 10 וקופסה 20. סטטוס DONE אם הקלט הסתיים, ERROR אם מצב לא מוכר, כמות שלילית או סוללה התחלתית לא חוקית; עצרו לפני שינוי בעקבות אירוע שגוי. החזירו `(left, right, case, denied, status)`. אפס חוקי; כל הערכים שלמים.

**דרך עבודה:**
- נסחו לפחות שלושה כללים שהמערכת חייבת לשמור עליהם. הגדירו מה קורה בקלט ריק, בקלט חריג ובערך גבול.
- כתבו פסאודו-קוד או תרשים זרימה לפני הפתרון. ציינו מתי משתנה המצב, מתי הנתונים מתעדכנים ומתי עוצרים.
- כתבו פונקציה עצמאית עם שמות משתנים בעלי משמעות. אל תשנו את הקוד הקיים; הוא משמש להשוואה.
- הוסיפו קריאות לפונקציה עם `print`. אין צורך ב-input בשלב הזה כדי שכל הצוותים יוכלו להריץ אותם מקרי בדיקה. מי שמסיים יכול להוסיף ממשק input בנפרד.
